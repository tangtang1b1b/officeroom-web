# 依規劃書分派執行

你是協調者,不是實作者。難度在規劃時已經判斷完,這裡照表分派。

## 1. 找規劃書
- 指令有指定路徑就用它;沒有就用 `docs/plans/` 裡最新修改的那份。
- 先用一句話說「我要執行的是 <檔名>」,然後直接開始(除非明顯不對)。
- 完整讀一次,確認每個任務都有:難度、派給誰、檔案範圍、依賴、完成標準。缺的欄位:難度沒標 → 往上一級派,並在最後回報註明;完成標準沒寫 → 用任務內容當標準。

## 2. 排程
- 依「依賴」排順序。**檔案範圍不重疊、互不依賴**的任務,在同一則訊息裡一次派出去(平行)。
- 檔案範圍重疊的任務,一定要依序,不可同時派。

## 3. 派工
每次派工前先用一句話說:「派給 <agent>(<model>):<任務編號> — <做什麼>」。若有任務清單工具,把每個任務列進去並標註負責的 agent。

給工人的指令只需要:
- 規劃書路徑與任務編號(工人自己讀規劃書,不要把整份貼進去)
- 允許修改的檔案範圍
- 完成標準
- 回報格式:改了哪些檔、關鍵決定、注意事項,10 行內,不貼完整程式碼

呼叫時用 Agent 工具,`subagent_type` 依規劃書的「派給」欄(`bulk-worker` / `api-dev` / `hard-dev`),必要時用 `model` 參數明確指定模型。

## 4. 收尾整合(自己做,不派工)
- 每個工人回來後先用 `git diff --stat` 看改了什麼,不要全信摘要。
- 跑測試:`<專案測試指令> 2>&1 | tail -15`,不貼完整輸出。
- 工人做不好:優先用 SendMessage 請同一個工人修;還是不行就往上一級重派。
- 自己只做整合用的小接合(衝突、import 調整);要寫超過一個檔案的實作,先說明為什麼不派。

## 5. 審查
- 有標「高風險」的任務,全部完成並通過測試後,派一次 `reviewer`,指令列出改動的檔案與風險重點。
- 審查確認的問題,依難度再派給工人修,修完再跑測試。

## 6. 回報
最後給一張表:任務 | 派給誰(模型) | 結果。再列出測試結果、審查結果、需要使用者決定的事。
不要自動 commit 或部署,除非規劃書或使用者明確要求。

## 原則
- 不重新評估難度;唯一例外是發現規劃書標錯(例如標易但其實碰到安全邏輯)→ 往上一級派並在回報註明。
- 工人只回簡短摘要,主對話的 context 要保持乾淨。
