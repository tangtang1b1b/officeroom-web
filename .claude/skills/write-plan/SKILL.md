# 寫規劃書

目標:把討論的結論變成一份「不需要讀對話就能照著做」的規劃書,讓便宜的協調者只要照表分派。難度與風險在這裡就要判斷完,這是整個流程最需要腦力的一步。

## 步驟
1. **整理已決定的事**:從討論裡抽出目標、已決定事項、明確不做的事。列出還沒決定的事;只有「不決定就無法動工」的才問使用者,其餘寫進規劃書的「待決事項」。
2. **拆任務**:每個任務要小到一個工人能獨立完成。盡量讓不同任務改不同檔案(才能平行);必須改同一個檔案的任務標成有先後相依。
3. **標難度與派工對象**(下表),不確定就往上一級:

   | 難度 | 判斷標準 | 派給 |
   |---|---|---|
   | 易 | 機械、規則一致、套用現有模式、文字或樣式調整、批次改多個檔案 | `bulk-worker`(haiku) |
   | 中 | 依現有慣例的一般功能,侷限在單一模組,有相鄰程式可參照 | `api-dev`(sonnet) |
   | 難 | 伺服器權威與安全、權限、前後端共用的核心邏輯、並發與時序、資料遷移、金流、沒有現成模式的架構決定 | `hard-dev`(opus) |

   凡是難度「難」,或牽涉安全、共用核心、資料遺失、金流的任務,標「高風險」,最後會送 `reviewer`。
4. **寫檔**:用同資料夾的 `plan-template.md` 為範本,存成 `docs/plans/<今天日期>-<英文短名>.md`(資料夾不存在就建立)。每個任務都要有:編號、內容、難度、派給誰、檔案範圍、依賴、完成標準。
5. **最後固定輸出兩件事**:
   - 一句話摘要:有幾個任務、各難度各幾個、哪些可平行、哪些是高風險、有哪些待決事項。
   - 一個可以直接複製的程式碼區塊,裡面的檔名要是真實路徑:

     ```text
     使用 dispatch skill,依 docs/plans/<實際檔名>.md 執行。
     規劃書已標好各任務的難度與派工對象,照標記分派,不要重新判斷難度。
     完成後回報:各任務由誰完成、測試結果、需要我決定的事。
     ```
   - 並提醒:在這個對話直接說「執行規劃書」也可以,但對話很長時,新開對話貼上這段比較省。

## 注意
- 這個 skill 只寫規劃書,不開始實作。
- 規劃書裡不要放長篇程式碼,只放決定與完成標準;細節讓工人自己讀程式。
